# Project Athena

A research-grade, end-to-end AI system that ingests football (soccer) match telemetry — from StatsBomb's open event/360 data, and now also from broadcast video via a parallel Computer Vision pipeline — and produces real-time tactical intelligence: goal-probability forecasting, spatial weak-spot detection, and a counterfactual "what-if" simulator. Two additional, entirely additive reporting capabilities sit on top of the StatsBomb track: historical player/team analysis reports (with a live Streamlit UI), and season-by-season team trend data from a second, non-StatsBomb source.
 
**Data provided by [StatsBomb](https://statsbomb.com).** The StatsBomb-track features throughout this project (player/team reports, team comparison, the shot map) are built on StatsBomb's open event/360 data, used under their Public Data User Agreement — see [ADR-020](docs/adr/ADR-020-statsbomb-open-data-licensing-scope.md) for the full licensing review, including the attribution requirement (clause 1.4) this notice and `dashboard.py`'s own sidebar satisfy.

This repository has grown across numbered milestones 1 through 45, plus several further additions made after the numbering convention lapsed (see `docs/FULL_PROJECT_REPORT.md` for the exact, verified timeline and an explicit note on when/why numbering stopped). **This page exists to disambiguate the documents** — to tell you which one to open for what you're actually trying to do.

## Quick start

```bash
pip install -r requirements-lock.txt            # exact versions this project was built/validated against
# or: pip install -r requirements.txt            # unpinned, human-readable, grouped-by-track list instead
cp .env.example .env                             # optional -- fill in whichever keys you actually need (all optional, see the file itself)
python -m production.src.pipeline.train        # full StatsBomb training pipeline (expensive)
scripts/run_tests_grouped.sh                     # full test suite -- 6 separate processes, NOT `pytest production/tests/` (see below)
mlflow ui                                        # inspect logged runs (from repo root)
uvicorn production.src.serving.api:app --reload  # live WebSocket/REST API
streamlit run production/frontend/dashboard.py   # live dashboard (7 tabs: CV monitor + 6 reporting/alerts tabs)
```

`requirements-lock.txt` (new, engineering-review action item) is a full `pip freeze` snapshot — every direct and transitive package pinned to the exact version this project's real results were produced against. `requirements.txt` stays unpinned and grouped by track for readability. See `requirements-lock.txt`'s own header for two honest caveats found while generating it (a `torch` local-version-suffix quirk, and `python-dotenv` having been an undocumented-but-real dependency until this pass — now added to `requirements.txt`).

This direct-process path (`uvicorn` + `streamlit`) is the only deployment path this repository documents or supports — Docker packaging was attempted, never validated end-to-end, and has since been removed from this repository (see the Docker row above).

## Running the test suite

**Use `scripts/run_tests_grouped.sh`, not a single `pytest production/tests/` invocation.** A real OOM incident (Aug 2026: two kernel OOM-killer terminations in one night, ~9.2GB peak RSS) found that running all ~44 test files / 250+ tests as ONE process lets PyTorch, MLflow, a YOLO checkpoint, PyTorch Geometric, and matplotlib all stay resident simultaneously for the whole run — none of that memory is returned to the OS mid-run (Python's own allocator, and especially PyTorch's caching allocator, hold onto freed memory for reuse rather than releasing it). `scripts/run_tests_grouped.sh` instead runs the suite as six separate `pytest` processes, grouped by subsystem (`cv`, `models`, `pipeline`, `reporting`, `serving-api`, `dashboard`) — each group's process exits and the OS reclaims its memory before the next group starts.

```bash
scripts/run_tests_grouped.sh          # full suite, 6 groups, -q by default
scripts/run_tests_grouped.sh -v       # verbose, forwarded to every group
pytest production/tests/test_api.py   # any single file/test still works exactly as before -- only the FULL-suite command changed
```

Measured peak RSS per group (the run that validated this fix): `cv` 2.91GB, `models` 1.12GB, `pipeline` 1.21GB, `reporting` 1.50GB, `serving-api` 1.28GB, `dashboard` 8.46GB — every group well clear of the ~9.2GB level that triggered the real OOM kills, **except `dashboard`, which stays close to it on its own** (`test_dashboard.py`'s ~30 tests are individually heavy: full Streamlit AppTest re-executions plus real HTTP against a real uvicorn server). Splitting into groups removes the risk of stacking `dashboard` on top of other files' overhead (the combined pre-split group hit 8.27GB and produced 6 reproduced-as-flaky test failures under that pressure) but does not, on its own, shrink `test_dashboard.py`'s own baseline — see `scripts/run_tests_grouped.sh`'s own header comment for the full investigation and the honest note that further splitting `test_dashboard.py` itself is a real, not-yet-taken next step if this becomes a problem again.

A smaller, secondary fix from the same investigation: `api.py`'s `lifespan` (which loads the MLflow model and warms the YOLO checkpoint) was being re-triggered up to 36 times within one `pytest` session by repeated `with TestClient(app) as client:` blocks in `test_api.py` alone, needlessly reloading the same deterministic model every time. Now idempotency-guarded (`if _model is None`, `_yolo_checkpoint_warmed`) — measured ~18% peak-RSS reduction on `test_api.py` alone, real but nowhere near sufficient by itself; the process-level grouping above is what actually fixed the OOM.

## Public deployment mode

Set `PUBLIC_DEPLOYMENT=true` in the environment of **both** the `api.py` process and the `dashboard.py` process before deploying this app somewhere the general public can reach it (a free, non-monetized public site — see [ADR-021](docs/adr/ADR-021-statsbomb-free-public-deployment-scoping.md) for the licensing scoping this flag enforces). Unset, or set to anything other than `"true"` (the default): behavior is identical to local/private research use, unchanged from before this flag existed.

What the flag changes when set:

- **Shot map** (`/reports/player/{player_id}/shot-map`): serves and renders only an aggregated shot-density / mean-xG grid — no individual shot's exact location is ever computed or returned on this path. Local/private mode (flag unset) continues to show the real per-shot scatter plot exactly as before. See ADR-021's Update section for the full reasoning.
- **Pass Network** (`/reports/pass-network/{match_id}`): serves and renders only per-player total pass counts and network-level summary stats (density, edge count) — no player's average location and no pairwise completed-pass count between two named players is ever computed or returned on this path. Local/private mode continues to show the real network graph (per-player average location, real pairwise edges). See ADR-021's "Condition 2 Applied to the Pass Network" Update section for the full reasoning, including why this needed the SAME treatment as the shot map rather than the season heatmap's exemption.
- **Player Dashboard touch map** (`/reports/player/{player_id}/match/{match_id}/touch-map`): serves and renders only a grid-binned touch-density heatmap — no individual touch's exact location is ever computed or returned on this path. Local/private mode continues to show the real per-touch scatter plot.
- **Player Dashboard key-event timeline** (`/reports/player/{player_id}/match/{match_id}/timeline`): serves and renders only event-type counts per coarse (15-minute) time bucket — no individually-enumerated event (exact minute, outcome, body part) is ever computed or returned on this path, since condition 2 bans "an interactive table of raw events" regardless of whether a location is attached. Local/private mode continues to show the real per-event timeline. The Player Dashboard's match-by-match **summary table** (`/reports/player/{player_id}/match-summary`) is NOT gated by this flag — per-match totals (minutes, event-type counts) are the same aggregate-count class of data the existing player report already serves unconditionally. See ADR-021's "Condition 2 Applied to the Player Dashboard's Match-Level Views" Update section for the full per-view reasoning.
- **Team Trends tab**: disabled entirely, with a visible explanation in its place. This tab's data source (football-data.co.uk, via `team_trend_data.py`) has its own separate, already-documented restriction — personal, non-distributed research use only — that a public deployment of the dashboard would otherwise silently violate regardless of this flag's effect on the shot map. See `team_trend_data.py`'s own docstring and [ADR-018](docs/adr/ADR-018-consolidate-reporting-behind-api-boundary.md)'s Update section.

The shot map and Team Trends fixes were found via a dedicated compliance audit that checked every user-facing feature against ADR-021's condition 2 ("no raw StatsBomb data exposed to site visitors") after the fact; the Pass Network and Player Dashboard's gating was instead resolved BEFORE implementation, per-view, following that audit's discipline proactively rather than reactively — everything else audited (positional distribution, the aggregate heatmap, team reports, team comparison, the What-If simulator, the StatsBomb-sourced live tactical stream, the Player Dashboard's own match-summary table) was already compliant by construction and needed no gate.

See `context.md` §2 for the full directory layout and module table, and `docs/FULL_PROJECT_REPORT.md` for the complete verified history.
